# المرحلة الرابعة: قاعدة المعرفة والبحث

أُنجزت متطلبات [todo3.md](../todo3.md) فوق نظام المشاريع والملفات السابق. أضيفت التصنيفات، ومقالات Markdown، والبحث الموحد في المقالات وأسماء الوثائق ومحتوى PDF النصي وDOCX. الواجهة عربية RTL، والتنزيل يمر دائمًا عبر صلاحيات FastAPI.

## الاستخدام

1. شغّل `docker compose up --build -d` من الجذر. يُطبّق Alembic الترحيل `0004` قبل تشغيل الخلفية والفهرسة.
2. افتح http://localhost:8080 ثم «قاعدة المعرفة». يستطيع المسؤول إدارة التصنيفات وإنشاء مقال عام أو مرتبط بمشروع، ويستطيع المدير إنشاء مقالات مشاريعه.
3. اكتب العنوان والملخص ومحتوى Markdown، واختر التصنيف واللغة والنطاق. احفظ مسودة أو احفظ وانشر. تمنع الواجهة المغادرة مع تعديلات غير محفوظة، وتتيح معاينة القوائم والروابط والكود.
4. المقال المنشور يظهر للقراء المصرح لهم. الأرشفة تُخرجه فورًا من البحث وقراءة الموظفين. قوائم المحررين تعرض المسودات والأرشيف عند اختيار الحالة المناسبة.
5. افتح «البحث الموحد»، وابحث بالعربية أو الإنجليزية. يمكن تصفية النتائج حسب النوع والمشروع والتصنيف واللغة والتاريخ، وترتيبها حسب الصلة أو التاريخ أو العنوان، والتنقل بين الصفحات.
6. بعد رفع PDF أو DOCX، تظهر حالة الفهرسة داخل تفاصيل الملف. يستطيع المسؤول إعادة محاولة فهرسة ملف فاشل. الملفات المصورة والصور تبقى قابلة للبحث بالاسم، دون OCR.

لا تُحمّل الصفحة الأولى من التصنيفات أو المشاريع وتفترض اكتمالها؛ أدوات الاختيار تدعم التصفح. تُحمّل صفحات المعرفة ومكتبة Markdown عند الحاجة لتقليل حجم الحزمة الأولى.

## القرارات والصلاحيات

التصنيفات عامة، من مستوى واحد، وإدارتها للمسؤول فقط. لا يمكن حذف تصنيف مرتبط بمقال؛ انقل المقال أو أزل تصنيفه أولًا. المعرف النصي `slug` فريد لكل نوع، ويُولّد من العنوان عند عدم إدخاله، ويقبل الحروف العربية والإنجليزية والأرقام والشرطات.

| العملية | Admin | Manager | Employee |
| --- | --- | --- | --- |
| إنشاء/تعديل/حذف تصنيف | نعم | لا | لا |
| إنشاء وتعديل ونشر وأرشفة مقال عام | نعم | لا | لا |
| إدارة مقالات المشروع | جميع المشاريع | المشاريع التي يديرها | لا |
| قراءة مسودات وأرشيف المشروع | جميعها | المشاريع التي يديرها | لا |
| قراءة المقالات العامة المنشورة | نعم | نعم | نعم |
| قراءة المنشور الخاص بمشروع | جميعها | المشاريع التي يديرها | المشاريع المنضم إليها |
| البحث في ملفات المشاريع | جميعها | المشاريع التي يديرها | المشاريع المنضم إليها |
| عرض سجل تعديل المقال | نعم | مقالات مشاريعه | لا |
| إعادة فهرسة ملف | نعم | لا | لا |

عضوية المدير في مشروع يديره مدير آخر لا تمنحه صلاحياته. مشاريع الأرشيف للقراءة فقط، بما فيها مقالاتها. المقال المؤرشف لا يُعدّل أو يُعاد نشره في هذه النسخة. لا يتغير نطاق مقال محفوظ بين الشركة والمشاريع؛ أنشئ مسودة جديدة للنطاق الجديد. الحساب المعطّل لا يستطيع استخدام البحث أو القراءة.

البحث الموحد يعرض **المنشور فقط، حتى للمسؤول**، والملفات غير المحذوفة فقط. إدارة المسودات والأرشيف تتم من قائمة المقالات المصرح بها. لا يوجد حذف نهائي للمقالات في الواجهة؛ الأرشفة تحفظ السجل.

## البيانات والمعاملات

| الجدول | الغرض والعلاقات |
| --- | --- |
| `knowledge_categories` | الاسم والوصف وslug والمنشئ وتواريخ الإنشاء والتعديل |
| `knowledge_articles` | العنوان والملخص وMarkdown والتصنيف الاختياري والمشروع الاختياري والمؤلف والحالة واللغة والتواريخ وحقول البحث |
| `activity_logs` | المستخدم والمقال والفعل والتاريخ؛ إنشاء وتعديل ونشر وأرشفة في معاملة المقال نفسها |
| `file_search_index` | علاقة فريدة `file_id` مع الملف السابق؛ النص المستخرج والحالة والخطأ ووقت الفهرسة وعلامة حجز العامل وحقول البحث |

المقال يبدأ `draft`، ثم يُنشر بمحتوى غير فارغ، ويمكن أرشفته. يوجد حد 50,000 حرف للمحتوى، و200 للعنوان، و1,000 للملخص. يبقى Markdown الأصلي، بما فيه مسافات الكود، دون تطبيع أو تعديل؛ التطبيع خاص بالبحث. تمنع قيود قاعدة البيانات الحالات واللغات غير المقبولة، وslug المكرر، والمحتوى الأطول من الحد، وحذف تصنيف مستخدم. تُرجع التعارضات `409`، والمدخلات غير الصالحة `422`، والمحتوى غير المتاح `404`.

تُحدّث PostgreSQL حقول البحث عبر triggers داخل معاملة تعديل المقال أو الملف. فشل المعاملة لا يترك فهرسًا أو سجل نشاط جزئيًا. إنشاء سجل الملف ينشئ مهمة فهرسة واحدة حتى لو أُضيف السجل خارج مسار الرفع. الترحيل يضيف مهامًا للملفات الموجودة قبل هذه المرحلة.

## البحث والصلاحيات

`GET /api/search` يقبل `q` (1–200 حرف)، و`type=all|article|file`، و`project_id` و`category_id` و`language=ar|en` و`updated_from/updated_to`، و`sort=relevance|newest|oldest|title`، و`page/page_size` بحد 100 نتيجة للصفحة. النتيجة تحتوي النوع والعنوان والمقتطف والمشروع والتصنيف ودرجة الصلة وتاريخ التحديث، إضافة إلى العدد والتصفح. التصنيف واللغة يخصان المقالات؛ اختيارهما يستبعد الملفات.

تُبنى نتائج المقالات والملفات باستعلامي SQL مقيّدين بالصلاحيات الحالية، ثم `UNION ALL`. يحدث عدّ النتائج وترتيبها و`LIMIT/OFFSET` على النتائج المصرح بها فقط. تُولّد المقتطفات بعد اختيار الصفحة. لا تُحمّل المكتبة إلى Python لتصفيتها، ولا تُخزن قوائم مستخدمين في الفهرس؛ تغيير المدير أو العضوية يسري في الطلب التالي دون انتظار خدمة الفهرسة. النص المستخرج غير متاح كمسار API مستقل، والتنزيل يعيد التحقق من صلاحية الملف.

أوزان `tsvector`: العنوان A، والملخص B، والمحتوى C. تُجمع متجهات الإعدادين العربي والإنجليزي، ويُستخدم `websearch_to_tsquery` مع معاملات مربوطة بدل دمج نص المستخدم في SQL. الترتيب الأساسي `ts_rank_cd` مع زيادة لتطابق العنوان، ثم ترتيب ثابت بالتاريخ والنوع والمعرف. تُطبّق مهلة SQL مقدارها خمس ثوانٍ لكل استعلام بحث.

العربية تستخدم إعدادًا باسم `public.workspace_arabic` مبنيًا على `simple`، مع دالة `workspace_normalize` على المدخل والمحتوى. تزيل التشكيل والتطويل، وتوحّد أشكال الألف والهمزة والياء، وتعالج اختلاف «مسئول/مسؤول»، وتزيل «الـ» من الكلمات الأطول وفق قاعدة محدودة. أثبتت الاختبارات أمثلة «إدارة/ادارة»، و«ملفات/الملّفات»، و«مسئول/مسؤول»، و«على/علي». هذه **قواعد تطبيع محدودة وليست محللًا صرفيًا عربيًا**؛ لا نعد بتوحيد جميع الجذور أو المرادفات. الإنجليزية تستفيد من إعداد PostgreSQL `english`، مثل `manage/management` حسب قاموسه.

يدعم `pg_trgm` التشابه في العناوين، بعتبة `word_similarity_threshold=0.45`. يُفعّل فقط لاستعلام بسيط من كلمات ومسافات، طوله من 4 إلى 80 حرفًا؛ لا يُفعّل للاستعلامات ذات عوامل البحث أو الرموز. أثبت اختبار `onboadring` إيجاد `onboarding`. لا تُطبق المطابقة التقريبية على أجسام المستندات كلها.

توجد فهارس GIN لمتجه المقال ومتجه الملف، وفهارس trigram للعناوين المطبعة، وفهارس للحالة والتصنيف والمشروع والتاريخ وطابور الفهرسة. إضافة GIN لا تلغي تكلفة عدّ وفرز أعداد كبيرة من النتائج.

المقتطف نص عادي محدود الطول، وعلامات التمييز محارف منفصلة تحولها React إلى `<mark>`، دون `dangerouslySetInnerHTML`. عرض Markdown بواسطة `react-markdown` مع تجاهل HTML، وحجب الصور الخارجية، وتقييد بروتوكولات الروابط؛ لا ينفّذ JavaScript من المقال أو المقتطف.

## الفهرسة واستخراج الوثائق

تعمل خدمة `indexer` منفصلة عن API، وتقرأ Volume الملفات بوضع القراءة فقط. لا ينتظر الرفع استخراج النص، ولا يتغير الملف الأصلي عند الفشل. حالات المهمة:

```text
pending → processing → ready
                     → failed
```

يختار العامل مهمة بواسطة `FOR UPDATE SKIP LOCKED`، ويحجزها بعلامة lease داخل معاملة قصيرة. ثم يستخرج النص خارج المعاملة في عملية Python فرعية. إذا توقف العامل، يُستأنف الحجز المتقادم بعد 90 ثانية افتراضيًا. تتحقق معاملة الحفظ من علامة الحجز وحالة الحذف؛ عامل قديم لا يستبدل نتيجة أحدث أو يعيد نص ملف محذوف. تمنع فريدة `file_id` تكرار المهام.

يستخدم PDF مكتبة `pypdf` للنص القابل للاستخراج فقط، دون OCR، مع حد للصفحات ومدخلات xref. يستخدم DOCX قراءة `word/document.xml` بمحلل `defusedxml` مع حد 8MiB للجزء المفكوك. كلاهما يحد النص المستخرج افتراضيًا بـ100,000 حرف. PDF المصور أو الصور يصل إلى `ready` دون نص، مع بقاء البحث بالاسم. فشل الاستخراج يبقي الاسم قابلًا للبحث والتنزيل متاحًا حسب الصلاحيات.

في Docker: حد ذاكرة الخدمة 768MiB، ومعالج واحد، و64 عملية. العملية الفرعية على Linux محدودة بذاكرة افتراضية 512MiB و10 ثوانٍ CPU، ويقتلها العامل عند تجاوز مهلة 15 ثانية. الحماية بحدود Linux تُختبر في الحاوية؛ تشغيل Windows المباشر لا يملك `RLIMIT`، لكنه يملك مهلة العملية وحدود النص والصفحات. تسجل الأخطاء معرف الملف ورمز الخطأ فقط، دون المحتوى أو كلمات المرور. الحالات الفاشلة لا تعاد آليًا بلا حد؛ يُعيد المسؤول المحاولة.

إعدادات `.env.example`، وتحتاج `docker compose up -d` بعد تعديلها:

| الإعداد | الافتراضي | المجال |
| --- | --- | --- |
| `INDEX_POLL_SECONDS` | 2 | 0.1–60 ثانية |
| `INDEX_TIMEOUT_SECONDS` | 15 | 1–60 ثانية |
| `INDEX_LEASE_SECONDS` | 90 | 90–600 ثانية |
| `INDEX_MAX_TEXT_CHARS` | 100000 | 1000–200000 حرف |
| `INDEX_MAX_PAGES` | 200 | 1–500 صفحة |

أوامر التشغيل والتشخيص:

```powershell
docker compose logs --tail 100 indexer
docker compose exec backend python -m app.search_maintenance --check
# يعالج مهمة واحدة أو يفرغ الطابور عند تشغيله يدويًا:
docker compose run --rm --no-deps indexer python -m app.index_worker --once
docker compose run --rm --no-deps indexer python -m app.index_worker --drain
# يعيد احتساب متجهات المقالات ويضع الملفات الحية في الطابور ثم يعالجها:
docker compose run --rm --no-deps indexer python -m app.index_worker --rebuild --drain
```

الأمر الأخير يعيد توليد بيانات البحث، ولا يحذف الوثائق أو المقالات. هذه إعادة بناء من المحتوى الأصلي؛ إصلاح فهرس PostgreSQL المادي نفسه يتم عبر `REINDEX` عند الحاجة التشغيلية، وليس مطلوبًا بعد كل تعديل مقال. عند التطوير خارج Docker، شغّل `python -m app.index_worker` في نافذة ثالثة بنفس `DATABASE_URL` و`FILE_STORAGE_PATH` الخاصين بالخلفية.

## API

التوثيق التفصيلي بالحقول والتحقق عبر http://localhost:8000/docs ضمن `Knowledge & Search` ومسارات الملفات. طلبات التعديل تحتاج جلسة وترويسة `X-Requested-With: WorkSpace` مع Origin المسموح، مثل المرحلة السابقة.

| المسار | العمليات |
| --- | --- |
| `/api/knowledge/categories` | GET قائمة متصفحة، POST إنشاء للمسؤول |
| `/api/knowledge/categories/{id}` | GET، PATCH، DELETE؛ الحذف يمنع الارتباط بمقالات |
| `/api/knowledge/articles` | GET قوائم حسب الصلاحية، POST مسودة |
| `/api/knowledge/articles/{id}` | GET قراءة، PATCH تعديل للمخولين |
| `/api/knowledge/articles/{id}/publish` | POST نشر |
| `/api/knowledge/articles/{id}/archive` | POST أرشفة |
| `/api/knowledge/articles/{id}/activity` | GET آخر 100 حدث للمحررين المخولين |
| `/api/search` | GET البحث الموحد للمنشور والوثائق المصرح بها |
| `/api/files/{id}/index` | GET الحالة والخطأ ووجود نص، دون النص المستخرج |
| `/api/files/{id}/reindex` | POST إعادة المحاولة للمسؤول |

## الاختبارات والأداء

التحقق في هذه المرحلة: **57 اختبار خلفية ناجحًا على PostgreSQL**، ثم إعادة تشغيل اختبارات المعرفة الستة بعد ضبط المقتطفات وحالة الفهرسة؛ **4 اختبارات متصفح ناجحة** على PostgreSQL، تشمل تسجيل الدخول والمشاريع والوثائق والمعرفة. نجح بناء TypeScript/Vite وفحص ترحيلات Alembic مقابل النماذج.

فحص تبعيات التشغيل `npm audit --omit=dev` أعاد صفر ثغرات. فحص ESLint الكامل ما زال يتوقف عند خطأين موجودين قبل هذه المرحلة، في `useResource.ts` و`Users.tsx`، متعلقين بقاعدة `set-state-in-effect`. الملفات الجديدة لم تضف أخطاء ESLint؛ نجاح البناء والمتصفح لا يعني نجاح فحص lint الكامل.

تغطي الاختبارات التطبيع العربي والإنجليزي والتشابه، والمحتوى الخاص وعدده ومقتطفاته، وإزالة العضوية وتغيير الإدارة، والتحديث والأرشفة الفوريين، والحقن، والتصفية والتصفح، والتعارضات والتراجع عن المعاملة، واستخراج PDF وDOCX، والملف المفقود والمهلة والحجز المتقادم وإعادة المحاولة، وبقاء التنزيل صالحًا عند فشل الاستخراج. اختبار المتصفح يغطي المعاينة الآمنة والتنبيه قبل مغادرة المحرر والقراءة دون أزرار تعديل للموظف والعرض على الهاتف.

من `backend`، استخدم قاعدة **اختبار مستقلة**؛ الاختبارات تنشئ جداولها وتحذفها، ولا يجوز استخدام قاعدة التطبيق:

```powershell
$env:TEST_DATABASE_URL = 'postgresql+psycopg://workspace:YOUR_DB_PASSWORD@localhost:5433/workspace_test'
.venv/Scripts/python -m pytest -q
```

الاختبارات القديمة تستطيع استخدام SQLite، لكن اختبارات البحث الأصلي تتطلب PostgreSQL. SQLite ليس بديل تشغيل لهذه المرحلة؛ مسار البحث يعيد `503` فيه، والاختبارات الخاصة بإمكانات PostgreSQL لا تثبتها SQLite.

لاختبارات المتصفح من `frontend`، أنشئ قاعدة مستقلة تنتهي بـ`_browser_test`:

```powershell
$env:BROWSER_TEST_DATABASE_URL = 'postgresql+psycopg://workspace:YOUR_DB_PASSWORD@localhost:5433/workspace_browser_test'
npm run test:e2e
npm run build
```

الاختبار يهيئ هذه القاعدة ويحذف جداولها، ويستخدم ملفات مؤقتة. دون المتغير يبقى تشغيل المتصفح القديم على SQLite ويُتخطى اختبار المعرفة الذي يحتاج البحث الأصلي.

قياسات فعلية محلية على PostgreSQL 17 في Docker: 50 تصنيفًا و10,000 مقال و20,000 سجل ملف بنص مستخرج تجريبي، في قاعدة فارغة مستقلة. تقرير [phase-04-performance.json](phase-04-performance.json) يتضمن `EXPLAIN ANALYZE` قبل GIN وبعده:

| القياس | النتيجة |
| --- | --- |
| وسيط بحث نادر، 5 عينات، دون فهارس البحث GIN | 266.65ms |
| وسيطه مع GIN | 80.09ms |
| أقصى عينة مع GIN | 103.40ms |
| عبارة شائعة، 10,002 نتيجة، صفحة 20 | 1229.06ms |
| العبارة الشائعة، صفحة 100 | 1178.27ms |
| عدد SELECT في صفحتي 20 و100 | 4 في كل منهما؛ دون N+1 |
| 8 أبحاث نادرة بأربعة خيوط | 433.03ms إجمالًا |
| ذروة ذاكرة Python لصفحة 20 | 253,740 بايت وفق tracemalloc |

خطة المطابقة انتقلت من Seq Scan إلى Bitmap Index Scan عبر GIN. زمن البحث الكامل يتضمن الجمع والصلاحيات والعدّ والترتيب والتشابه والمقتطفات، ولا يساوي زمن عقدة المطابقة وحدها. القياسات محلية وليست ضمان SLA. العبارة الشائعة بقيت نحو 1.2 ثانية بسبب عدد المطابقات والعدّ والترتيب؛ يجب قياس أحمال الإنتاج قبل توسيع النظام. ذاكرة Python المذكورة لا تشمل PostgreSQL أو نظام التشغيل، والبيانات التجريبية لا تقيس زمن استخراج 20,000 وثيقة فعلية.

لإعادة القياس، أنشئ قاعدة **فارغة** تنتهي بـ`_search_benchmark`، واضبط `TEST_DATABASE_URL` إليها، ثم شغّل `.venv/Scripts/python -m tests.benchmark_search` من `backend`. يزيل الاختبار فهارس البحث مؤقتًا في هذه القاعدة فقط، ثم يعيدها ويحذف بياناته في النهاية ويكتب التقرير.

## Docker والنسخ الاحتياطي والأخطاء

أثبت فحص Docker أن مقالًا ووثيقة DOCX ومهمة معلقة بقيت بعد إعادة تشغيل قاعدة البيانات والخلفية، وأن العامل استأنف المهمة وأصبح محتوى كليهما قابلًا للبحث. أُصلح إعداد Nginx ليعيد حل اسم `backend` عبر DNS الخاص بـDocker عند تغيّر عنوان الحاوية.

أصبح `scripts/backup_workspace.py backup-and-check` يوقف `indexer` مع الواجهة والخلفية أثناء أخذ نسخة متسقة، ثم يعيد الخدمات ويستعيد النسخة في بيئة منفصلة. يراجع أحجام وSHA-256 للوثائق، ثم وجود إعداد البحث والمتجهات ومهام الملفات. نجح الفحص بوجود مقال ووثيقة مفهرسة؛ تبقى تعليمات الحماية والاحتفاظ من [المرحلة الثالثة](phase-03.md) سارية. ملفات النسخ محلية خاصة ومستثناة من Git.

- **البحث يعيد 503:** استخدم PostgreSQL و`alembic upgrade head`؛ لا تدعم SQLite إمكانات البحث المطلوبة.
- **إعداد اللغة أو pg_trgm غير موجود:** تحقق من نجاح خدمة `migrate` وصلاحية مستخدم قاعدة البيانات لإنشاء الامتداد والإعداد والدوال. لا يثبت البحث بنجاح ترحيل SQLite.
- **ملف pending/processing طويلًا:** تحقق من خدمة `indexer` واتصالها وقيم الإعدادات وVolume؛ الحجز المتقادم يُستأنف بعد مهلة lease.
- **ملف failed:** راجع رمز الخطأ دون نشر محتوى الملف. `missing_file` يعني غياب الأصل؛ `timeout/resource_limit` تجاوز الحدود؛ `extraction_failed` فشل التحليل. أصلح السبب وأعد الفهرسة من تفاصيل الملف بحساب المسؤول.
- **ready دون نص:** ملف مصور/صورة أو لا نص قابل للاستخراج؛ البحث بالاسم يعمل. لا يوجد OCR في هذه المرحلة.
- **تعديل مقال لا يظهر في البحث:** يجب أن يكون منشورًا ومصرحًا به. استخدم فحص `search_maintenance` ثم إعادة البناء عند وجود خلل؛ النصوص الجديدة تتحدث عبر triggers فور المعاملة.
- **HTTP 502 بعد تبديل حاوية الخلفية:** تحقق من صحة الخلفية وانتظر تحديث DNS القصير في Nginx؛ الإعداد الحالي يعيد الحل كل عشر ثوانٍ.

تفصل الفهرسة عن الصلاحيات عمدًا: الفهرس يصف المحتوى، واستعلام الطلب يقرر الوصول الحالي. لا OCR أو RAG أو بحث دلالي أو خدمة خارجية في هذه النسخة.

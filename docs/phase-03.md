# المرحلة الثالثة: ملفات المشاريع

المتطلبات وقائمة الإنجاز في [todo2.md](../todo2.md). تضاف الوثائق داخل صفحة تفاصيل المشروع، دون مشاركة عامة أو معاينات أو إصدارات متعددة.

## التشغيل والتخزين

```powershell
docker compose up --build -d
```

تُطبّق Alembic `0003` قبل بدء API، ويُنشأ Volume مستقل اسمه `workspace_file_data` ومربوط بـ`/data/files`. يعمل Backend كمستخدم غير root، والمجلد خاص به. لا توجد StaticFiles أو روابط عامة للتخزين؛ Nginx يمرر `/api` فقط. تغيير أو إعادة إنشاء الحاوية يحتفظ بالملفات ما دامت Volumes محفوظة. لا تستخدم `docker compose down -v` على بيانات تحتاجها.

| المتغير | الافتراضي | المعنى |
| --- | --- | --- |
| `FILE_STORAGE_PATH` | `.data/files` خارج Docker، و`/data/files` داخله | مجلد التخزين الخاص |
| `MAX_UPLOAD_BYTES` | `10485760` | الحد الفعلي، من بايت واحد حتى 10MiB |
| `FILE_AUDIT_INTERVAL_SECONDS` | `3600` | فترة فحص الاتساق؛ أقلها 60 ثانية |

الحد المذكور في الواجهة 10MB يعني هنا 10 × 1024 × 1024 بايت. تعرض الواجهة الحد المضبوط من `/api/files/policy`. يترك Nginx مساحة لغلاف multipart بحد 11MiB ويعطّل buffering لطلبات API، بينما يحسب API البايتات الفعلية للجسم بحد الملف + 64KiB للغلاف، ثم يتحقق من حجم الملف نفسه أثناء نسخه على أجزاء 64KiB. لا يثق بـ`Content-Length` وحده.

## البيانات واتساقها

`files`: UUID، مراجع المشروع والرافع، الاسم الأصلي، مفتاح تخزين UUID مستقل وفريد، MIME الفعلي، الامتداد المعتمد، الحجم، SHA-256، تاريخ الرفع والحذف المنطقي. المفاتيح الخارجية RESTRICT، والقيود تمنع الأحجام الفارغة أو الأكبر من 10MiB والامتدادات غير المعتمدة. فهارس المشروع/الحذف/التاريخ، والرافع/التاريخ تدعم القوائم. لا تُرسل استجابات API مفتاح التخزين أو المسار الداخلي.

ترتيب الرفع:

1. التحقق من الجلسة والصلاحية وحالة المشروع قبل استهلاك multipart.
2. تحليل ملف واحد فقط، مع حدود للجسم وعدد الحقول والملفات. يرحّل UploadFile الملفات الكبيرة إلى ملف مؤقت بدل الاحتفاظ بها كاملة في RAM.
3. نسخه إلى `.tmp` الخاص على أجزاء، وحساب الحجم وSHA-256، ثم flush وfsync والتحقق من البنية.
4. إعادة فحص نشاط المستخدم وعضويته وحالة المشروع تحت قفل صف المشروع، تحسبًا لتغيّرها أثناء الرفع.
5. نقل ذري إلى اسم UUID على نظام الملفات نفسه ثم حفظ السجل ومعاملته.
6. حذف المؤقتات دائمًا، وحذف الملف النهائي إذا فشل الإدخال أو ثبت أن المعاملة لم تُحفظ.

إذا فشل الاتصال أثناء commit فقد تكون PostgreSQL حفظت المعاملة بالفعل. يحاول النظام التحقق من النتيجة باتصال مستقل. إذا بقيت النتيجة مجهولة، يحتفظ بالمحتوى النهائي بدل احتمال حذف ملف محفوظ، ويسجّل الحالة لفحص الاتساق. انقطاع العملية قسرًا بين النقل والحفظ يمكن أن يخلّف ملفًا يتيمًا؛ لا توجد معاملة ذرية مشتركة بين القرص وPostgreSQL.

أقصى معالجتي تحقق/نسخ متزامنتين في عملية Backend الواحدة. تجاوزهما يرجع 429 قابلًا لإعادة المحاولة. النسخة المحلية تستخدم Worker واحدًا؛ هذا الحد ليس محددًا موزعًا متعدد الخوادم.

## أنواع الملفات والتحقق

| النوع | الفحص |
| --- | --- |
| `.pdf` | توقيع PDF، وpypdf strict، شجرة صفحات صالحة، حتى 2000 صفحة و100,000 مدخل xref. الملفات المشفرة مرفوضة. يستخدم القارئ مقبض ملف قرصيًا بدل نسخ الملف كله إلى BytesIO. |
| `.png` | توقيع PNG، وفحص Pillow للبنية ثم فك الصورة للتأكد من عدم تلف بياناتها. |
| `.jpg`, `.jpeg` | توقيع JPEG وفحص Pillow وفك الصورة. |
| `.docx` | توقيع ZIP، CRC، وجود Content Types وعلاقة officeDocument وword/document.xml الصحيحة، وفحص XML آمن بـdefusedxml. |

الصور محدودة بـ25 مليون بكسل. DOCX محدود بـ2000 عنصر و50MiB بعد فك الضغط و8MiB لكل XML ونسبة ضغط 200:1. تُرفض المسارات الصاعدة والمطلقة والروابط الرمزية والتشفير والعناصر المكررة وملفات VBA والملفات المضمنة التنفيذية. لا يتم استخراج ZIP إلى القرص أو جلب روابط خارجية. اسم الملف الأصلي لا يُستخدم لبناء أي مسار؛ تُرفض محاولات traversal ومحارف التحكم والمسارات المشفرة.

MIME المرسل من المتصفح غير موثوق؛ يُستنتج النوع المعتمد من التوقيع والبنية، ويجب أن يتوافق مع الامتداد. هذه فحوص بنيوية وليست مضاد فيروسات؛ قد يظل مستند صالح البنية ضارًا عند فتحه. الإضافة المستقبلية لفحص ClamAV خارج نطاق هذه المرحلة. توثيق الأساس: [FastAPI UploadFile](https://fastapi.tiangolo.com/tutorial/request-files/)، [حدود وتحليل multipart في Starlette](https://starlette.dev/requests/)، [Pillow والتحقق وحدود الصور](https://pillow.readthedocs.io/en/stable/reference/Image.html)، [pypdf PdfReader](https://pypdf.readthedocs.io/en/stable/modules/PdfReader.html).

## الصلاحيات

- Admin: عرض وتنزيل جميع الملفات ورفعها وحذفها في أي مشروع غير مؤرشف.
- Manager: نفس الإجراءات في المشاريع التي يديرها فقط؛ عضويته في مشروع مدير آخر لا تمنحه الوصول.
- Employee: عرض وتنزيل ورفع الملفات في مشاريع عضويته؛ يحذف ملفه فقط ما دام عضوًا والمشروع غير مؤرشف.
- الحساب المعطّل مرفوض. معرفة معرف الملف لا تمنح الوصول إليه.
- الأرشفة تسمح بالعرض والتنزيل، وتمنع الرفع والحذف. حالات Planning وCompleted وغيرها لا تعني الأرشفة.
- الحذف يضبط `deleted_at` ويمنع المعلومات والتنزيل ويخفي الملف من القائمة. لا يحذف المحتوى فعليًا ولا يحرر المساحة. لا توجد استعادة أو عملية إزالة نهائية آلية في هذه المرحلة.

## API

| الطريقة | المسار | النتيجة |
| --- | --- | --- |
| GET | `/api/files/policy` | الحد والأنواع المسموحة لمستخدم مسجّل |
| POST | `/api/projects/{id}/files` | ملف واحد في حقل `file` باستخدام multipart، ثم 201 وMetadata |
| GET | `/api/projects/{id}/files` | قائمة مقسمة إلى صفحات بعد الصلاحيات والفلاتر |
| GET | `/api/projects/{id}/file-uploaders` | رافعو الملفات النشطة المتاحة للمستخدم، لاختيار فلتر |
| GET | `/api/files/{id}` | معلومات الملف المسموح دون مسارات داخلية |
| GET | `/api/files/{id}/download` | تنزيل على أجزاء مع attachment وMIME الفعلي وnosniff وCSP sandbox |
| DELETE | `/api/files/{id}` | حذف منطقي؛ 204 |

كل طلب يتطلب الجلسة. POST وDELETE يتطلبان `X-Requested-With: WorkSpace` وOrigin مسموحًا كما في المرحلة الأولى. Swagger على http://localhost:8000/docs يعرض حقل اختيار الملف.

الفلاتر: `q`, `type=pdf|png|jpg|jpeg|docx`, `uploaded_by` (UUID)، و`sort_by=original_name|size_bytes|created_at` و`sort_order=asc|desc` و`page` و`page_size` (1–100). فلتر JPEG يشمل jpg وjpeg. تعاد `{items,page,page_size,total,total_pages}`. يجري البحث والفرز والعد وLIMIT/OFFSET في PostgreSQL، مع معرف ثابت كفاصل تعادل في الترتيب. البحث يعامل `%` و`_` كنصوص.

```sh
# بعد تسجيل الدخول وحفظ Cookie محليًا في cookies.txt
curl -b cookies.txt -H "X-Requested-With: WorkSpace" -F "file=@guide.pdf" http://localhost:8080/api/projects/PROJECT_UUID/files
curl -b cookies.txt -OJ http://localhost:8080/api/files/FILE_UUID/download
```

الأخطاء: 400 للفارغ أو الاسم/الطلب غير الصالح، 401 للجلسة، 403 للصلاحيات، 404 للمفقود/المحذوف، 409 للأرشيف أو اختلاف الحجم المخزن، 413 للحجم، 415 للنوع أو البنية، 422 للمدخلات، 429 لازدحام المعالجة، 503 للتخزين/قاعدة البيانات، و500 للخطأ غير المتوقع. لا ترجع أخطاء نظام الملفات أو SQL. إذا فشلت القراءة بعد بدء إرسال استجابة التنزيل، يُقطع البث، ويتيح Content-Length للعميل اكتشاف عدم اكتماله.

## فحص الاتساق والصيانة

```powershell
docker compose exec backend python -m app.file_audit
docker compose exec backend python -m app.file_audit --verify-checksums --strict
```

يفحص Backend الاتساق كل ساعة بعد بدء التشغيل، ويسجل الأعداد فقط عند وجود مشكلة. يشمل الفحص سجلات الملفات المحذوفة منطقيًا، ويحسب مساحتها المحتجزة. يمنح الملفات غير المرتبطة مهلة ساعة لتجنب اعتبار رفع جارٍ ملفًا يتيمًا، ويبلغ عن المؤقتات الأقدم من يوم. لا يحذف أو يعدّل أي شيء. خيار checksums يعيد قراءة المحتوى على أجزاء؛ strict يرجع رمز خروج غير صفري عند فقدان/اختلاف المحتوى أو تعذر الوصول.

## النسخ الاحتياطي والاستعادة المختبرة

يتطلب السكربت Docker Compose وPython. الأرشيف يحتوي على مستندات الشركة وبيانات الحسابات، ويجب تقييد الوصول إليه وحفظ نسخة آمنة خارج القرص نفسه. `backups/` مستبعد من Git. Volumes لا تغني عن النسخ الاحتياطي.

```powershell
# من المجلد الرئيسي
backend/.venv/Scripts/python scripts/backup_workspace.py backup-and-check

# نسخة دون إعادة اختبار
backend/.venv/Scripts/python scripts/backup_workspace.py backup

# استعادة اختبارية لنسخة موجودة
backend/.venv/Scripts/python scripts/backup_workspace.py restore-check backups/BACKUP_DIRECTORY
```

يوقف الإنشاء frontend وbackend الجاريين مؤقتًا لوقف الكتابة، ثم ينتج `database.dump` بـpg_dump و`files.tar` من Volume الخاص و`manifest.json` بأحجام وبصمات الأرشيفين، ويعيد الخدمات التي كانت تعمل. يجب إيقاف أي كاتب خارجي إضافي أثناء النسخ أيضًا. الفشل لا ينتج manifest مكتملًا يمكن اعتماده.

الاستعادة هنا **استعادة فعلية إلى بيئة اختبار مستقلة**: تتحقق من بصمات الأرشيف، تنشئ PostgreSQL وVolume جديدين بلا منافذ مضيف، تنفذ pg_restore وتعيد الملفات بمستخدم الخدمة، ثم تطابق كل سجل وحجمه وSHA-256، بما فيها الملفات المحذوفة منطقيًا. تحفظ `restore-check.json` ثم تزيل حاويات وVolumes الاختبار فقط. لا تكتب فوق قاعدة الشركة. لاستعادة تشغيلية، اتبع نفس ترتيب الاستعادة إلى بيئة جديدة معزولة، تحقق من التقرير قبل تحويل التطبيق إليها؛ استبدال البيئة الحالية ليس جزءًا من هذا الأمر الآمن.

نجحت تجربة الاستعادة بملف نشط وآخر محذوف منطقيًا، كما نجح التحقق من بقاء المحتوى بعد restart وبعد force-recreate دون حذف Volumes. حُذفت بيانات الفحص وحسابها ومحتواها المؤقت من التطبيق بعد التحقق.

## الاختبارات والأداء

النتيجة النهائية: **49 اختبار Backend على PostgreSQL و3 اختبارات متصفح Edge ناجحة**، مع نجاح بناء React/TypeScript وDocker وفحص ترحيل Alembic دون فروق. اختبارات الملفات الجديدة 30 حالة ضمن المجموعة. يوجد تحذير deprecation غير مانع من Starlette حول عميل الاختبارات httpx؛ لم يؤثر في النتائج.

```powershell
# من backend
.venv/Scripts/python -m pytest -q
# لتشغيل PostgreSQL استخدم قاعدة اختبار منفصلة وفارغة، لا قاعدة الشركة
$env:TEST_DATABASE_URL = 'postgresql+psycopg://workspace:YOUR_DB_PASSWORD@127.0.0.1:5433/workspace_test'
.venv/Scripts/python -m pytest -q
# من frontend
npm run build
npm run test:e2e
```

اختبارات الملفات تشمل الأنواع الأربعة، تزوير المحتوى، ZIP/XML الخبيث، حد 10MiB الحقيقي والجسم دون Content-Length، الصلاحيات قبل قراءة الطلب وبعد التحقق من المحتوى، الحساب المعطل، الأرشفة، الحذف المنطقي، التنزيل المطابق، أسماء متكررة، أخطاء القرص وspooling، فشل SQL قبل وبعد commit، والتنظيف وفحص الاتساق. يختبر المتصفح أسماء عربية ورفعًا ناجحًا وفاشلًا وتنزيلًا مطابقًا وحذف الموظف لملفه فقط، والتصفية والعرض على الهاتف. الاختبارات تستخدم تخزينًا مؤقتًا لا Volume الشركة.

لتكرار الأداء، أنشئ قاعدة فارغة ينتهي اسمها بـ`_files_benchmark`:

```powershell
docker compose exec db createdb -U workspace workspace_files_benchmark
# من backend
$env:BENCHMARK_DATABASE_URL = 'postgresql+psycopg://workspace:YOUR_DB_PASSWORD@127.0.0.1:5433/workspace_files_benchmark'
.venv/Scripts/python -m tests.benchmark_files
```

التقرير [phase-03-performance.json](phase-03-performance.json) يقيس 5,000 ملف و50 مشروعًا. عدد SELECT ثابت (5) لصفحات 20 و100 عنصر مع جلب الرافع دون N+1. أظهرت EXPLAIN استخدام فهرس الملفات. في القياس المحلي، PDF حجمه نحو 4MiB احتاج نحو 0.6MiB من تخصيصات Python القصوى لمسار النسخ/التحقق/الحفظ. هذا القياس لا يشمل المتصفح أو multipart spooling أو تخصيصات المفككات الأصلية؛ فك الصور أو XML يحتاج ذاكرة إضافية ضمن الحدود المذكورة. نجح رفع ملفين بالاسم نفسه بالتزامن وتنزيل ثمانية ملفات بأربعة خيوط. ليست هذه الأرقام ضمان أداء للإنتاج أو قياس RSS كاملًا.

## مشاكل شائعة

- 413: اختر ملفًا أصغر من الحد الظاهر. حد Nginx أعلى قليلًا لغلاف multipart؛ لا ترفع حد API فوق 10MiB في هذه النسخة.
- 415: تأكد من أن المستند صالح فعلًا، غير مشفر، وبالامتداد الصحيح، وليس ملفًا أعيدت تسميته. بعض الصور الكبيرة جدًا أو DOCX ذي ضغط/تضمينات غير مسموحة يُرفض رغم أن حجمه صغير.
- 503: افحص مساحة القرص وصلاحيات Volume ثم سجلات Backend؛ رسائل المستخدم لا تكشف المسارات.
- 404 لملف له سجل: شغّل audit، ثم افحص النسخة الاحتياطية. لا تنشئ سجلًا بديلًا أو ملفًا فارغًا مكانه.
- عند تشغيل Backend خارج Docker يستخدم `.data/files` المحلية، ولا يرى Volume Docker تلقائيًا. أثناء تطوير React يمكنك إبقاء Backend داخل Docker. لا تستخدم قاعدة Metadata واحدة مع مخزنين منفصلين؛ طابق نسخة قاعدة البيانات ومحتواها ومسار التخزين عند نقل بيئة التطوير.
- 409: المشروع مؤرشف، أو اختلف حجم المحتوى عن Metadata. افحص audit قبل محاولة إصلاح يدوي.
- 429: انتظر انتهاء رفع جارٍ ثم أعد المحاولة.
- لا تظهر ملفات لمستخدم: تحقق من العضوية أو مدير المشروع وحالة الحساب، ثم الفلاتر. معرفة UUID لا تمنح صلاحية.

لا يتيح التخزين المحلي مشاركة الحالة بين عدة خوادم. التوسع يتطلب تخزينًا مشتركًا/Cloud وخطة فحص ملفات وإدارة حصص وتنظيف احتفاظ؛ خارج نطاق هذه المرحلة.
